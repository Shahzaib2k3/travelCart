# API reference

All endpoints return JSON. Everything except `POST /api/auth/login` needs a valid session cookie (`tc_session`), which the login call sets.

## Common responses

| Status | Meaning |
|---|---|
| 200 / 201 | Success / created |
| 400 | Validation failed. The body has `error` (the first message) and, for bookings, `issues` (a list of `{ path, message }`) |
| 401 | Not signed in, or the account is inactive |
| 403 | Signed in, but the role is not allowed to do this |
| 404 | Not found |
| 409 | Conflict (for example, a duplicate email) |

## Roles

| Capability | Admin | Agent |
|---|---|---|
| Create, view, search, edit bookings | Yes | Yes |
| Delete bookings | Yes | No |
| See Total Sold, Ticket Cost, Profit | Yes | Yes (demo setting, one line to change) |
| Filter bookings by creator | Yes | No |
| User Management endpoints | Yes | No |

These rules live in `src/lib/permissions.ts` and `src/lib/auth.ts`.

## Authentication

### POST /api/auth/login

Body: `{ "email": "...", "password": "..." }`
200: `{ "ok": true, "role": "ADMIN" | "AGENT" }` and sets the session cookie.
Errors: 400 invalid input, 401 `Invalid email or password` (the same message for an unknown email), 403 `This account has been deactivated`.

### POST /api/auth/logout

200: `{ "ok": true }`. Ends the session.

### GET /api/auth/me

200: `{ "user": { "id", "fullName", "email", "role", "status" } }`. 401 if not signed in. Also refreshes the 30-minute inactivity timer.

## Users (Admin only)

### GET /api/users

200: `{ "users": [ { id, fullName, email, role, status, createdAt, lastLoginAt } ] }`

### POST /api/users

Body: `{ fullName, email, password, confirmPassword, role }` where `role` is `ADMIN` or `AGENT`.
Password rules: at least 8 characters, with an upper case letter, a lower case letter and a number.
201: `{ "user": { ... } }`. 400 validation, 409 `A user with this email already exists`.

### GET /api/users/:id

200: `{ "user": { ... } }`. 404 if not found.

### PATCH /api/users/:id

Body (any of): `{ fullName, email, role, status }` where `status` is `ACTIVE` or `INACTIVE`.
200: `{ "user": { ... } }`. 400 if the change would deactivate or demote the last active Admin. 404, 409 duplicate email.
Deactivation takes effect immediately, because the account status is re-checked on every request.

### POST /api/users/:id/password

Body: `{ password, confirmPassword }`. 200: `{ "ok": true }`. Existing passwords can never be read.

## Bookings

### POST /api/bookings: create

Body:

```json
{
  "idempotencyKey": "8f0c237f-a04a-4a01-bf24-4d41c878c85d",
  "customerName": "Ayesha Malik",
  "phone": "+44 7700 900123",
  "email": "ayesha@example.com",
  "bookingType": "FULL_PAYMENT",
  "journeyType": "RETURN",
  "cabinClass": "ECONOMY",
  "airline": "Emirates",
  "departureAirport": "LHR",
  "destinationAirport": "DXB",
  "departureDate": "2026-12-20",
  "returnDate": "2027-01-05",
  "travellers": [
    { "passengerType": "ADULT", "title": "MR", "firstName": "Ali", "middleName": null,
      "lastName": "Khan", "dateOfBirth": "1990-05-01" }
  ],
  "totalSold": "1200.10",
  "ticketCost": "950.20",
  "paymentMethod": "CARD",
  "notes": "Optional text"
}
```

Allowed values:

- `bookingType`: `PAYMENT_PLAN`, `PAYMENT_AWAITING`, `FULL_PAYMENT`, `DATE_CHANGE`
- `journeyType`: `ONE_WAY`, `RETURN`, `MULTI_CITY`
- `cabinClass`: `ECONOMY`, `PREMIUM_ECONOMY`, `BUSINESS`, `FIRST`
- `passengerType`: `ADULT`, `CHILD`, `YOUTH`, `INFANT`
- `title`: `MR`, `MRS`, `MS`, `MISS`, `MSTR`
- `paymentMethod`: `BANK_PAYMENT`, `CARD`, `INTERNATIONAL_CARD`, `KLARNA`, `CLEARPAY`, `PAYPAL`

Rules:

- `RETURN` needs `returnDate`, which cannot be before `departureDate`
- `MULTI_CITY` replaces the four route fields with `"segments": [ { departureAirport, destinationAirport, departureDate, airline? } ]`, with at least two, in date order
- Airports are 3-letter IATA codes, and departure and destination must differ
- Money is sent as text with at most 2 decimals (`"1200.10"`)
- At least one traveller is required, and dates of birth cannot be in the future
- **Profit is never sent.** The server calculates it as `totalSold - ticketCost`

Behaviour:

- The reference (`TC-2026-000001`) is generated by the server from an atomic yearly counter, inside the same transaction that saves the booking, its travellers and its segments. Either everything is saved, or nothing is.
- `idempotencyKey` (optional but sent by the form) prevents duplicates. Sending the same key again returns the original booking with `"duplicate": true` and status 200.
- `createdBy` and `updatedBy` come from the session, never from the body.

201: `{ "booking": { ...see "Booking object" } }`

### GET /api/bookings: list, search, filter

Query parameters (all optional):

| Parameter | Meaning |
|---|---|
| `q` | Searches reference, customer name, phone and email (case-insensitive, partial) |
| `bookingType`, `journeyType` | Exact filters |
| `airline` | Partial match |
| `departureFrom`, `departureTo` | Departure date range (`YYYY-MM-DD`) |
| `createdFrom`, `createdTo` | Creation date range (inclusive) |
| `createdBy` | User id. **Admin only** (403 for Agents) |
| `sort` | `createdAt` (default), `departureDate`, `totalSold`, `profit`, `customerName`, `reference` |
| `dir` | `asc` or `desc` (default `desc`) |
| `page`, `pageSize` | Pagination. `pageSize` defaults to 10 and is capped at 100 |

200: `{ "bookings": [ ... ], "page", "pageSize", "total", "totalPages" }`. Deleted bookings never appear. If a role cannot see financials, those fields are removed and sorting by them is ignored.

### GET /api/bookings/:idOrReference

The path accepts the internal id or the reference (`TC-2026-000001`).
200: `{ "booking": { ... } }`. 404 if missing or deleted.

### PUT /api/bookings/:idOrReference: update

Body: the same shape as create (without `idempotencyKey`). Travellers and segments are replaced inside one transaction.

- The reference **cannot change**, because it is never read from the request
- Profit is recalculated on every update
- `updatedBy` and `updatedAt` are set automatically
- 403 if the role may not edit, 400 validation, 404

200: `{ "booking": { ... } }`

### DELETE /api/bookings/:idOrReference

Admin only (403 otherwise). This is a **soft delete**: the row is kept with a `deletedAt` date and disappears from every list, search and total. References are never reused.
200: `{ "ok": true }`

### Booking object

```json
{
  "id": "...", "reference": "TC-2026-000001",
  "customerName": "...", "phone": "...", "email": "...",
  "bookingType": "...", "journeyType": "...", "cabinClass": "...",
  "airline": "...", "departureAirport": "LHR", "destinationAirport": "DXB",
  "departureDate": "2026-12-20", "returnDate": "2027-01-05",
  "paymentMethod": "CARD", "notes": "...",
  "totalSold": "1200.10", "ticketCost": "950.20", "profit": "249.90",
  "travellers": [ { id, passengerType, title, firstName, middleName, lastName, dateOfBirth, sortOrder } ],
  "segments": [ { id, segmentOrder, airline, departureAirport, destinationAirport, departureDate } ],
  "createdBy": { "id": "...", "fullName": "..." },
  "updatedBy": { "id": "...", "fullName": "..." },
  "createdAt": "2026-11-28T10:15:00.000Z", "updatedAt": "2026-11-28T10:15:00.000Z"
}
```

For multi-city bookings the top-level airports and departure date come from the first and last segments, so lists and filters behave the same for every journey type. `totalSold`, `ticketCost` and `profit` are omitted for roles without financial access.

## Dashboard

### GET /api/dashboard

200:

```json
{
  "counts": { "total": 36, "byType": { "PAYMENT_PLAN": 9, "PAYMENT_AWAITING": 9, "FULL_PAYMENT": 9, "DATE_CHANGE": 9 } },
  "financials": { "totalSold": "...", "ticketCost": "...", "profit": "..." },
  "recent": [ ...the five most recent bookings, list format... ]
}
```

The figures are calculated by the database (`COUNT`, `SUM`, `GROUP BY`) over non-deleted bookings, so they always match the real records. `financials` is only present for roles allowed to see it.

## Mapping to the assignment's API table

| Required function | Where it lives |
|---|---|
| Create Booking | `POST /api/bookings` |
| Generate Booking Ref | `nextReference()` in `src/lib/bookings.ts`, called inside the create transaction |
| Get All Bookings | `GET /api/bookings` |
| Get Booking by ID | `GET /api/bookings/:id` |
| Update Booking | `PUT /api/bookings/:id` |
| Delete Booking | `DELETE /api/bookings/:id` |
| Search Bookings | `GET /api/bookings?q=...` |
| Calculate Booking Profit | `calcProfit()` in `src/lib/bookings.ts`, run on every create and update |
| User Login | `POST /api/auth/login` |
| Create User | `POST /api/users` |
| Get All Users | `GET /api/users` |
| Update User | `PATCH /api/users/:id` |
| Reset Password | `POST /api/users/:id/password` |
| Activate / Deactivate User | `PATCH /api/users/:id` with `status` |
| Check Permissions | `requireApiUser()` in `src/lib/auth.ts` and `can()` in `src/lib/permissions.ts`, applied to every protected route |
